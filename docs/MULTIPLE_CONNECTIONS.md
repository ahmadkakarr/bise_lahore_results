# Wi-Fi and USB tethering for approved parallel registration

This opt-in direct-HTTP mode uses two or more fixed, operator-approved internet connections. Wi-Fi plus a phone's USB tethering is supported. It uses HTTPX, HTTPCore, AnyIO and Linux `SO_BINDTODEVICE` for physical routes. A separately opted-in fixed HTTP CONNECT proxy is described below. These Python packages were already installed and are now explicit dependencies. It does not configure the OS network, change gateways, rotate addresses or switch a refused attempt to another route.

The ordinary command without `--connections` keeps its existing single-connection behavior. Browser registration is unchanged. This implementation does not establish the portal's actual limiter scope or guarantee increased throughput.

## Connect and verify

Keep laptop Wi-Fi connected. When available, connect the phone by USB and enable mobile data and USB tethering. Each online interface needs an IPv4 address and default route. The configured phone may be absent at startup: Wi-Fi can start alone, and mobile workers resume automatically when the configured USB interface returns. If the phone shares the same Wi-Fi upstream, its public IP may be the same; the conflicting route pauses while the other continues.

On this laptop, USB takeover of the ordinary Wi-Fi route/DNS was observed and a persistent isolated routing profile was prepared. [USB routing fix and reconnect verification](USB_ROUTING_FIX.md). Default routes may live in dedicated policy tables; discovery includes them. The isolated profile selects a fixed device alias. The one-time stable-phone identity installation in that guide makes the same alias work across USB ports, while keeping DNS and ordinary default routing on Wi-Fi.

Run local discovery and a read-only public-IP check:

```sh
cd /home/ahmad/code/personal/bise_lahore_results && .venv/bin/python -m youthgames_register.connections discover --output connection_profiles/wifi-usb.json && .venv/bin/python -m youthgames_register.connections check --config connection_profiles/wifi-usb.json --pin
```

Discovery reads Linux routes and creates the config only when at least two connected default-route interfaces exist. It preserves an existing config and operator edits. For the observed phone, install the stable USB identity rule in [the routing guide](USB_ROUTING_FIX.md) so changing ports preserves its configured alias, isolated OS profile and saved route history. An unrelated USB device is never silently reassigned to that connection. `source_ip: null` selects the interface's single IPv4 address, accommodating DHCP changes. An interface with multiple IPv4 addresses requires an explicit source IP.

`check --pin` makes one HTTPS GET to `api.ipify.org` through each bound interface, confirms different global IPv4 egress addresses, then saves diagnostic pins in the local config. The service receives no applicant data. It sends no applicant POST and does not read or write the registration DB. The standalone `check` command without `--pin` remains a strict diagnostic comparison against those observations. Submission runners instead observe the current egress through the configured interfaces and accept naturally changed mobile/public IPs automatically. No manual re-pin is needed to start/resume registration, and the runner never changes internet routes or requests IP rotation. The allocation CLI may perform local input refresh/recovery before invoking the runner.

The [example config](../connection_profiles/wifi-usb.example.json) documents the schema; discovery fills actual interface names, so copying guessed USB interface names is unnecessary. Linux must permit binding sockets to each interface. With default `--auto-recover`, each route has its own readiness state and lock. Local carrier/source checks run about every two seconds; offline/reconnect probes retry about every five seconds, and verified public egress is refreshed periodically. A missing/offline route, ambiguous DHCP source or temporary egress failure pauses only that route. Startup proceeds when at least one configured route is verified; when all routes are offline the process waits. Ctrl+C interrupts waits and writes a stopped summary. Malformed configuration still fails with an actionable error. With `--no-auto-recover`, unavailable routes fail immediately. A disconnected USB client never silently sends its request through Wi-Fi.

For `source_ip: null`, each new TCP connection resolves the current IPv4 address on that same configured interface before binding and connecting. This handles DHCP changes without rebuilding the process. An explicitly configured source IP remains explicit. In-run safe form GET failures use the existing route cooldown/recovery loop. An unclear response after a dispatched POST remains uncertain; reconnect handling does not silently replay that POST.

## Run

Stop the old registration command with Ctrl+C and wait for committed receipts before starting the new one. The existing process lock prevents simultaneous commands from owning the registration DB. The new command safely skips previously completed applicants.

```sh
cd /home/ahmad/code/personal/bise_lahore_results && .venv/bin/python -m bise_allocate http-submit --config allocation_profiles/lahore_9th_raiwind.json --connections connection_profiles/wifi-usb.json --workers-per-connection 6 --prepare-ahead 2 --in-flight 6 --dispatch-interval 6 --limit 0 --auto-recover --retry-uncertain --uncertain-retries 2 --alarm
```

`--workers-per-connection 6` assigns six workers to EACH connection (12 total for Wi-Fi + USB). Alternatively, `--workers 12` means total workers split evenly; the two options are mutually exclusive. The combined software cap remains 36. Preparation and in-flight limits apply per connection. Two preparation slots keep fresh forms bounded; six in-flight slots allow slow responses to overlap without blocking the next dispatch. The example requests a six-second baseline per connection. An explicit `--dispatch-interval 5` replaces the old configured/non-throttle baseline, including an earlier saved six-second baseline; actual server-throttle spacing and all cooldown deadlines remain in force. Without an override, the old baseline remains. Five seconds is the local minimum. Two six-second routes have a theoretical combined ceiling near 20 starts/minute before latency, cooldowns and validation failures; this is not a portal quota guarantee.

New, undispatched work uses one shared indexed queue, claimed only by online workers. Wi-Fi can therefore continue through all available new work while the phone is unplugged, rather than leaving half the batch reserved for an absent device. Upon reconnect, the same mobile workers join new work again. Previously dispatched applicants and all retries have route affinity: their recorded connection's queue, cooldown and prior attempts are retained, including across restarts where stable route evidence exists. The system never moves a refused identity to another route to escape a cooldown. In-flight results are saved normally; a lost POST response retains uncertainty and uses the opt-in policy below. If only offline-route retries remain, the run waits for that route; if every selected record is resolved, it finishes even if the phone is still absent.

The initial form preflight uses an available route, preferring Wi-Fi. A temporary preflight connection failure or server cooldown on one route does not force the other route to wait for it. The independent health watcher never resets server pacing or replays a POST, and its tasks are cancelled/drained when the run ends.

## Optional Pakistan proxy

`--pakistan-proxy` adds the fixed endpoint in `connection_profiles/pakistan-proxy.json` to the explicitly configured Wi-Fi/USB routes. Without that flag the proxy config is never read and no proxy workers or requests are created. It requires `--connections`; `--proxy-config PATH` selects a different explicit profile and requires the opt-in flag. The preset endpoint was verified for page access only, not live applicant POST throughput. It is a public free endpoint whose uptime and ownership are not established by a successful GET.

```sh
cd /home/ahmad/code/personal/bise_lahore_results && .venv/bin/python -m bise_allocate http-submit --config allocation_profiles/lahore_9th_raiwind.json --connections connection_profiles/wifi-usb.json --pakistan-proxy --workers-per-connection 8 --prepare-ahead 2 --in-flight 6 --dispatch-interval 5 --limit 0 --auto-recover --retry-uncertain --uncertain-retries 2 --alarm
```

Eight workers per enabled route means 24 total across Wi-Fi, USB and proxy (the overall cap remains 36). To return to the two physical routes, omit only `--pakistan-proxy`. Proxy URL, diagnostic expected public IP and default interval are editable in its JSON. Syntax validation occurs before input preparation. This initial implementation accepts one public IPv4 HTTP proxy with an explicit port; credentials, hostnames, private/local addresses, SOCKS URLs, paths and query strings are rejected rather than silently interpreted. HTTPS to the portal and IP-echo service is tunneled with normal certificate verification. There are no additional dependencies.

The proxy uses the laptop's ordinary internet uplink to reach that endpoint; it is a separate egress route, not a third physical internet connection. It has isolated pooled clients/cookies, explicit proxy transport with no environment/direct fallback, its own preparation/in-flight bounds, durable dispatch clock and server/transport cooldowns. Its configured endpoint determines its stable identity; label or observed exit-IP changes do not reset clocks. A new endpoint is a new identity, and old dispatched applicants are not reassigned to it.

The existing `Connections · this run` dashboard shows `Pakistan Proxy` separately with worker count, POSTs, saved registrations, duplicate skips, uncertainty retries, spacing and online/offline state. Its workers also carry that label. Per-route counters are retained in `Current Progress.json`, run `Progress.json` and final `Summary.json`. IP-echo verification detects shared public egress and pauses the conflicting route. A failed proxy pauses only its own workers; online Wi-Fi/USB workers continue fresh work and the proxy rejoins after recovery. Temporary network waits and actual server cooldowns remain independent.

All three routes share the same registration ledger and atomic job claims. Completed applicants are skipped regardless of the enabled route set. Previously dispatched/uncertain retries retain their original route affinity. If the proxy flag is removed, its unresolved ready retries stay in SQLite and are reported as `deferred_disabled_connections`; they are not sent through Wi-Fi/USB. Re-enable the same proxy config to resume them. Other eligible work continues. A healthy proxy GET does not establish either the portal's permitted rate or successful registrations per minute.

## Recovery of a stalled mobile connection

The 20261022T103244130721Z run showed mobile transport errors building a cumulative retry counter to 16 and a 300-second local wait, despite zero observed throttle refusals. The route became online after USB reconnection, but the old wait remained. The original run eventually resumed (426 mobile successes observed during inspection); this was a prolonged local recovery delay rather than evidence of a fixed 295-submission portal quota.

Transport and server waits now have independent durable deadlines in `recovery_delays`. Network errors coalesce per connection, backing off 5, 10, 20, then at most 30 seconds. A successful portal form GET resets this streak. A verified physical reconnect or source/public-address transition clears only the transport wait and wakes existing waiters immediately. An IP-echo success alone after a portal error does not erase the portal retry streak. Genuine server Retry-After deadlines, throttle spacing, and receipt-derived cooldowns remain in force, including across restarts. Legacy combined deadlines remain conservative until expiry because their old reason alone cannot prove that no earlier server wait was included.

Every inner GET retry checks route readiness; offline workers wait without repeatedly attempting form requests. A failed GET closes/replaces its HTTPX pool. Each worker also replaces its pool before its next GET after the route generation changes. Previously prepared forms are refreshed after a verified reconnect; an in-flight POST is never cancelled/replayed by this handler. A new GET always establishes a fresh cookie/CSRF session. The opt-in uncertain-response policy below is unchanged.

The dashboard labels local transport waits as `retry in Ns` / `retrying`, actual server waits as `server cooldown Ns` / `server wait`, and disconnected routes as offline. Structured cooldown events include `kind: transport` and error class; `recovery_reset` records recovery while retaining the remaining server wait. Connection summaries include separate server/transport wait seconds and the transport retry round. Apply code updates by stopping the old command once with Ctrl+C, waiting for its summary, then restarting; running Python processes retain their old implementation.

Add `--retry-uncertain` to the command above to opt into a new attempt for prior uncertain applicants in the current pinned input. Default behavior without this flag remains blocked pending reconciliation. This option relies on the observed portal BForm duplicate rejection; it cannot guarantee exactly-once external delivery. It does not reset confirmed registrations or invent a tracking ID when the portal returns a duplicate message.

The previous attempt stays `uncertain` with its existing receipt. An append-only `uncertain_retries` row retains the full previous job snapshot, prior attempt ID, profile, run directory and authorization timestamp; the current job becomes Ready for a new attempt. Applicants with input conflicts, existing tracking, damaged payload hashes, invalid preparation, or identities outside this profile/roll selection are held. Other held uncertain jobs do not block this explicitly opted-in run.

With both `--retry-uncertain` and `--auto-recover`, new transport timeouts/unknown responses also receive up to `--uncertain-retries 2` extra attempts during this run, each after the same connection's durable backoff and with fresh form/CSRF. If still unresolved, the applicant stays uncertain with all receipts intact and other applicants continue. Set the count to zero to quarantine new unknown results immediately while continuing. This is bounded per applicant, not an infinite retry loop. KeyboardInterrupt/cancellation, local receipt/disk failures and worker programming errors still stop correctly; a confirmed success is never rewritten or retried after a post-processing error.

## Durable tracking

All routes use one SQLite connection, one registration process lock and the existing indexed portal/campaign/BForm ledger. Registered identities remain immutable and cannot start another attempt. A job is claimed atomically before its first network submission. The old receipt, tracking ID, raw identity and normalization history remain preserved.

New SQLite tables, created idempotently on a registration run:

- `connection_pacing`: per-stable-interface-key/campaign spacing, retry rounds and cooldown.
- `connection_dispatch_clock`: last dispatch for each connection, persisted atomically with intent/dispatch.
- `attempt_connections`: immutable route association for each dispatched attempt.
- `connection_slots`: stable interface identity and one-time legacy pacing inheritance.
- `connection_observations`: hashed public-IP observations recorded on startup/change between runs.

Connection keys are hashes of configured interface names and the identity policy version. Neither naturally changed public IPs nor renamed display labels reset pacing. At the first run of this policy, each route inherits the most restrictive legacy IP-keyed pacing/deadlines and latest dispatch clock because historical IP-to-device association may be unknown. Legacy rows and immutable attempt-route associations are retained unchanged. Later runs retain that interface's own cooldown and record changed public-IP hashes as observations. Earlier unscoped portal pacing and refusal deadlines remain inherited conservatively. Original single-connection pacing is retained. Restarting or changing worker count never resets confirmed registration states.

The dashboard shows a separate Connections table with friendly `Mobile USB` / `Wi-Fi` labels, online/offline state, worker counts, dispatched POSTs, saved registrations, already-registered skips, unresolved uncertain applicants and uncertainty retries for this run. Final summaries retain connection counts; JSON also includes `connection_online`, `workers_by_connection`, `connection_results` and effective pacing. Device names remain in private structured evidence. Each HTTP request proof records its route label/key and every received redirect hop's method/path/status/rate headers separately, including partial hops when a response is lost. Legacy combined headers remain for compatibility. Logs do not expose connection credentials, cookies or student identity fields.
